---

## 目的

Issueが少なくなったタイミングで、プロジェクトの改善候補を分析・提案してGitHub Issueを自動作成する。継続的な品質改善サイクルを止めないためのスキル。

## 自動発動条件（MCP経由のIssue操作時）

`mcp__github__update_issue` や `gh issue close` などでIssueをクローズ・完了状態に変更した**直後**に、以下を確認する：

```bash
gh issue list --state open --limit 50 --json number | jq length
```

残りopen Issue数が **1件以下** になっていた場合は、ユーザーに確認せずそのまま改善提案フローに入る。

> **なぜ自動で確認するか：** Issueが枯渇すると改善サイクルが止まる。操作のたびに残数チェックすることで、ユーザーが意識しなくてもサイクルを維持できる。

## ステップ

### ステップ1: 現状把握

まず以下を確認する（提案の重複を避けるために必須）：

```bash
# open Issueの確認
gh issue list --state open --limit 50

# 直近でクローズされたIssueの確認（同じ提案を繰り返さないため）
gh issue list --state closed --limit 20
```

GitHubリポジトリが不明な場合は `git remote -v` で確認する。

### ステップ2: コードベースの分析

プロジェクトの主要ファイルを調査して改善点を洗い出す。以下の優先順で分析する：

| 優先度 | カテゴリ | 着目すべき観点 |
|--------|----------|---------------|
| 1 | セキュリティ | 認証・認可の漏れ、入力バリデーション不足、機密情報の扱い、CORS設定。**設定ファイルに認証情報がある場合は必ず `git check-ignore` と `git log` で確認し、gitignore済み・未コミットであれば問題なしとする** |
| 2 | バグ・エラー修正 | エラーハンドリングの欠如、エッジケース未考慮、型の不整合 |
| 3 | パフォーマンス | 不要な再レンダリング、重いクエリ、N+1問題、キャッシュの欠如 |
| 4 | UX/UI改善 | ユーザーへのフィードバック不足、操作性の問題、アクセシビリティ |
| 5 | コード品質 | 重複コード、複雑すぎる関数、型安全性の欠如 |
| 6 | 機能改善 | 明らかに不足している機能、ユーザーが詰まりそうな箇所 |

**分析対象のディレクトリ：**
- `frontend/` — UIコンポーネント、状態管理、API呼び出し、フォームバリデーション
- `backend/` — APIエンドポイント、バリデーション、DB操作、認証・認可
- `infra/` — デプロイ設定、セキュリティグループ、環境変数の管理
- `docker-compose.yml` — サービス設定、ポート公開範囲

### ステップ3: 提案の選定（5件）

分析結果から **5件** を選定する。

選定基準：
- **ユーザーへの影響が大きい**ものを優先する
- **実装コストと効果のバランス**が良いものを選ぶ
- **既存のopen/closedIssueと内容が重複しない**ものに限る
- カテゴリが1つに偏らないようバランスを取る

### ステップ4: ユーザーへの提案確認

以下の形式で5件を提示し、確認を取る：

```
## 改善提案 (5件)

### 1. [タイトル]
- **カテゴリ:** セキュリティ / バグ / パフォーマンス / UX / コード品質 / 機能改善
- **優先度:** 高 / 中 / 低
- **問題:** 現状どういう問題があるか
- **改善内容:** 何をどう変えるか
- **該当箇所:** `path/to/file.ts`

### 2. ...
```

最後に「このままIssueを作成しますか？変更したい提案があれば教えてください。」と聞く。

### ステップ5: GitHub Issueの作成

ユーザーの承認後、各提案をGitHub Issueとして作成する。

**Issueタイトルの形式：**
```
[カテゴリ] 改善内容を端的に表すタイトル
```

例: `[セキュリティ] APIエンドポイントへの認証チェック追加`

**Issue本文のテンプレート：**

```markdown
## 問題

（現状の問題点を具体的に説明。なぜこれが問題なのかも書く）

## 改善内容

（何をどう変えるか。できるだけ具体的に）

## 該当箇所

- `path/to/file.ts`

## 期待される効果

（改善後にどうなるか、ユーザーや開発者にどんな恩恵があるか）
```

Issue作成には `gh issue create` または GitHub MCPツール（`mcp__github__create_issue`）を使う。
ラベルが既存のものと合うなら `--label` で付与する。

### ステップ6: 作成結果の報告

全Issue作成後、一覧を報告する：

```
## 作成したIssue (5件)

- #42 [セキュリティ] 〇〇 — https://github.com/...
- #43 [UX] 〇〇 — https://github.com/...
- #44 [パフォーマンス] 〇〇 — https://github.com/...
- #45 [バグ] 〇〇 — https://github.com/...
- #46 [コード品質] 〇〇 — https://github.com/...

次にIssueが残り1件になったら、また声をかけてください！
```
